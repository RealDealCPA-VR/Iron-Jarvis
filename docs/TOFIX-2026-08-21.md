## HIGH

### 1. `file_search` content mode reports an INVALID REGEX as "no matches"

- **Where:** `src/iron_jarvis/filesearch/service.py:273-275` (`search_content`), surfaced by `src/iron_jarvis/filesearch/tools.py:64-88`
- **Defect:** `search_content` wraps `re.compile(regex)` in `except re.error: return []`. The tool
  then returns `ok=True`, `output=""`, `data={"count": 0}` — indistinguishable from a genuine
  "this text is nowhere in your files". The sibling `grep` tool gets this right
  (`tools/builtins.py:854-855` returns `ToolResult(ok=False, error=f"bad regex: {exc}")`).
- **Failure scenario:** The agent searches for a literal containing a regex metacharacter — a
  function signature (`read_file(`), a Windows path (`C:\Users`), a bracketed name (`a[b`). The
  pattern fails to compile, the tool answers "0 results, ok", and the model tells the user the
  text does not exist. This is the "a silently short listing reads as complete and the model then
  says a file does not exist" failure the v1.153.1 rule exists to prevent, in the one tool meant
  to reach *outside* the workspace.
- **Evidence:** all three example patterns genuinely fail to compile, so the `count=0` below is the
  swallowed error and not a legitimate miss:
  ```
  're.error: missing ), unterminated subpattern'      for 'read_file('
  're.error: incomplete escape \U'                    for 'C:\Users'
  're.error: unterminated character set'              for 'a[b'

  query='read_file'   ok=True count=1  out='...a.py:1: def read_file(path):'
  query='read_file('  ok=True count=0  out='' err=None
  query='C:\\Users'   ok=True count=0  out='' err=None
  query='a[b'         ok=True count=0  out='' err=None
  ```
- **Mitigating fact (stated honestly):** the tool description does say `'content' (regex, default)`,
  so a model that escapes its literals is safe. The severity is about the failure *shape* — a
  wrong answer with no signal — not about likelihood.
- **Fix:** return the `re.error` as a tool error (grep's shape). Optionally fall back to
  `re.escape(query)` and SAY SO in the output — never a silent empty.

### 2. `file_search` and `grep` silently skip every file that is not valid UTF-8

- **Where:** `src/iron_jarvis/filesearch/service.py:213-216` (`_read_text`) and `src/iron_jarvis/tools/builtins.py:876-884` (`GrepTool`)
- **Defect:** Both hard-code `decode("utf-8")` and treat `UnicodeDecodeError` as "skip this file" —
  `_read_text` returns `None`, grep `continue`s. The file is then absent with no signal:
  `file_search` reports a lower count, and grep's truncation note (which does report the walk cap
  and the deadline) says nothing about undecodable files. The project already owns the right
  decoder — `documents/readers._decode_bytes:258` (utf-8-sig → strict cp1252 → charset-normalizer →
  latin-1), written because "cp1252/latin-1 office exports survive instead of turning into
  replacement characters", and used to close findings 25 and 26 of the previous review. The two
  search paths were never migrated onto it.
- **Failure scenario:** A CSV exported by Excel/QuickBooks/Lacerte (cp1252 — curly apostrophes,
  `€`, accented client names) sits in a searched root. The user asks "find every file mentioning
  the retainer". `file_search` returns only the UTF-8 files and reports a confident count; the
  cp1252 file and every client record in it is invisible. Searching the client's own name
  (`O'Brien`) returns zero with no indication a file was skipped.
- **Evidence:** two-file root, one cp1252 CSV + one UTF-8 CSV, both containing "Retainer":
  ```
  utf-8 decode of the cp1252 bytes: 'utf-8' codec can't decode byte 0x92 in position 14
  _decode_bytes round-trips the same bytes EXACTLY (U+2019 ’, U+20AC €, U+00E9 é)
  file_search 'Retainer' ok=True count=1  out='...ok.csv: Smith,Retainer fee'  <- cp1252 file missing
  file_search 'Brien'    ok=True count=0  out=''
  ```
- **Fix:** route both through `_decode_bytes` (verified above to decode these bytes correctly). If
  a file still cannot be decoded, COUNT it and report it — the truncation-is-reported rule applies
  to a skipped file exactly as it does to a truncated walk.

## MEDIUM

### 3. A non-ASCII signature header 500s the daemon's unauthenticated Slack route

- **Where:** `src/iron_jarvis/daemon/routes/comm.py:538` | also `src/iron_jarvis/webhooks/security.py:48` and `:94`
- **Defect:** `hmac.compare_digest` raises `TypeError` when both arguments are `str` and either
  holds a non-ASCII character. `slack_events` compares `expected` (str) against
  `request.headers.get("X-Slack-Signature")` (str, latin-1 decoded off the wire), so a signature
  header with any byte ≥ 0x80 raises instead of returning the intended 403.
  `/comm/slack/events/` is token-exempt (`daemon/auth.py:_is_exempt`), so it is reachable with no
  bearer token. `webhooks/security.verify` / `verify_signed` carry the identical defect on the
  token-protected `/webhooks/{slug}` route. This class was diagnosed and fixed for the bearer token
  in `daemon/auth.py:token_matches`, whose docstring explains it — *"Comparing BYTES makes every
  candidate comparable, so a wrong token is a plain 401 again."* The other three call sites were
  never brought in line.
- **Failure scenario:** With a Slack channel configured, an unauthenticated POST carrying
  `X-Slack-Signature: v0=caf\xc3\xa9` returns 500 with a traceback in the log instead of 403. An
  unhandled exception is the worst available outcome on the one route an unauthenticated caller can
  reach, it is triggerable on demand, and per this repo's history a 500 is the shape the dashboard
  renders as "daemon offline".
- **Evidence:** real uvicorn server, raw socket, `IRONJARVIS_TOKEN` set, **no bearer sent** — so
  this also confirms the exemption is what makes it reachable:
  ```
  ascii wrong signature -> HTTP/1.1 403 Forbidden  {"detail":"invalid slack signature"}
  non-ascii signature   -> HTTP/1.1 500 Internal Server Error
                           {"detail":"internal error: TypeError: comparing strings with
                            non-ASCII characters is not supported"}
  ```
- **NOT a security bypass** — this was graded HIGH in revision 1 and that was wrong. The signature
  still fails closed; nothing is authenticated that should not be. It is an error-contract and
  robustness defect, and it needs a configured signing secret to reach.
- **Fix:** encode both sides before comparing, exactly as `token_matches` does, at all three sites.

### 4. `Transfer-Encoding: chunked` bypasses `BodyLimitMiddleware` completely

- **Where:** `src/iron_jarvis/daemon/auth.py:146-147` (installed at `daemon/app.py:1087`)
- **Defect:** The cap is enforced by scanning the ASGI scope for a `content-length` header. A
  chunked request carries none, so the loop finds nothing, `break`s, and the body passes through
  unlimited — defeating the guard whose docstring says it exists so "an oversized JSON/base64 body
  … can't OOM/fill-disk the daemon".
- **Evidence:** real uvicorn, raw socket, global cap set to 1 MB, **the same valid 2 MB JSON body**
  sent two ways to `/documents/upload`:
  ```
  valid JSON, Content-Length  -> HTTP/1.1 413 Content Too Large
  valid JSON, chunked         -> HTTP/1.1 200 OK        <- accepted and written to disk
  ```
  The 200 is the whole finding: not merely "the middleware didn't fire" but "the over-cap request
  succeeded end to end".
- **Bound:** requires an authenticated caller (or an exempt path) that also passes the Host/Origin
  guard, so it is defence-in-depth rather than a drive-by. Graded LOW in revision 1; the 200 OK
  moves it to MEDIUM.
- **Fix:** count bytes as they stream through `receive` and 413 once the running total crosses the
  cap, instead of trusting a header.

### 5. All three blackboard tools run their whole SQLite workload on the event loop

- **Where:** `src/iron_jarvis/blackboard/tools.py:137` (`blackboard_post`), `:197` (`blackboard_read`), `:256` (`message_agent`)
- **Defect:** Each `async def execute` calls `store.board_id_for`, `store.name_for`, `store.list`,
  `store.roster` and `store.post` synchronously — no `asyncio.to_thread` anywhere in the module.
  `roster()` is the expensive one: `_seed_runs` (`blackboard/store.py:175-201`) fetches up to
  `_MAX_ROSTER_RUNS = 200` rows and calls `resolve_board_id` once per row, **each opening its own
  `session_scope`** — an N+1 with a fresh connection per iteration — before `_department_runs` does
  a bounded BFS on top.
  The same `roster()` is deliberately offloaded one layer up in `agents/runtime.py`
  (`teammates_block`), whose docstring reads *"SYNCHRONOUS ON PURPOSE, and therefore only ever
  called through `asyncio.to_thread` … measured `roster()` alone at up to 47ms in a pathological
  tree. On the daemon's single event loop that is 47ms of every request in the app."* The sibling
  substrate from the same release does it correctly too: `worklist/tools.py` wraps **every** store
  call (`:217`, `:268`, `:274`, `:446`, `:456`). Only the blackboard tools were left inline — and a
  tool runs once per model step, far more often than prompt assembly.
- **Evidence (corrected — revision 1 quoted only the worst case):** cost scales linearly with
  department size, warm SQLite on SSD:
  ```
  supervisor +   3 children,  10 posts ->   2.5 ms per blackboard_read
  supervisor +   5 children,  20 posts ->   3.2 ms
  supervisor +  10 children,  40 posts ->   4.8 ms
  supervisor +  40 children,  60 posts ->  14.8 ms
  supervisor + 100 children, 200 posts ->  35.9 ms   (approaching the author's own 47 ms figure)
  ```
  **At a realistic department size this is 2–3 ms, not 14.8 ms.** Revision 1 led with the 41-run
  number, which was an unrepresentative synthetic. The finding stands on the rule violation, the
  unbounded linear growth, and the N+1 — not on a dramatic measured stall.
- **Fix:** wrap each store call in `asyncio.to_thread` (copy `worklist/tools.py`). Separately,
  collapse `_seed_runs`' N+1 into one walk rather than 200 nested sessions.

### 6. Document-tool `capture_undo` / `revert` read, hash and spill whole files on the event loop

- **Where:** `src/iron_jarvis/documents/excel_tools.py:185` and `:799`; `src/iron_jarvis/documents/pdf_tools.py:173` and `:442`; `src/iron_jarvis/documents/tools.py:951`; `src/iron_jarvis/ltm/tools.py:128` and `:179`; the shared `src/iron_jarvis/tools/undo.py:288` and `:302-310`
- **Defect:** These `async def capture_undo` hooks call `target.read_bytes()` then
  `make_file_descriptor(...)`, which sha256s the whole payload and — above
  `INLINE_MAX_BYTES` (verified: **8 KB**, so every real document spills) — writes the pre-image to
  disk via `save_preimage`. All inline, no `to_thread`. `registry.invoke` awaits `capture_undo`
  *before* `execute`, so the file is read twice per call. `revert_workspace_file` is worse: it
  re-hashes the target, loads the pre-image blob and writes the whole file back, on the loop, and
  it is the shared revert for `write_file`/`edit_file` too.
  `tools/builtins.py` was explicitly brought in line for exactly this, with the comment *"OFF THE
  EVENT LOOP (v1.153.1's rule, applied here at last). This hook is awaited by `registry.invoke`
  BEFORE `execute` runs, so its stat + full read of the prior file blocks every other request in
  the daemon"* (`builtins.py:369-402`, `:457-480`). The document tools — the ones that handle
  scanned returns and client workbooks — were not.
- **Failure scenario:** The agent calls `excel_edit` on a client workbook or `pdf_merge` on a
  scanned return; the daemon freezes for the read+hash+spill, then again for `execute`'s own read.
  On an unhydrated OneDrive path or a network share (`workspace_root` is routinely the user's real
  folder since v1.189.0) the stall is bounded only by the OS, and Time Travel's undo of the same
  file freezes the app a third time.
- **Evidence:** verbatim `capture_undo` body, warm SSD — roughly **1.4 ms per MB**:
  ```
   1 MB ->  1.9 ms      10 MB -> 14.1 ms
   5 MB ->  7.0 ms      40 MB -> 58.5 ms   (measured event-loop stall: 58.5 ms, idle tick ~1 ms)
  ```
  A typical workbook is 2–7 ms; a 40 MB scanned return is ~59 ms, doubled by `execute`'s re-read.
- **Fix:** wrap each hook body in `asyncio.to_thread` — the one-line change `builtins.py` already
  carries — and offload `revert_workspace_file`'s hash/read/write.

### 8. `consult`'s per-run budget can be evicted while the run is still live

- **Where:** `src/iron_jarvis/agents/consult_tool.py:206-216`
- **Defect:** `_charge` writes `self._consults[key] = (used + 1, started)`. Re-assigning an
  **existing** dict key does not move it to the end of the insertion order, and `_prune` evicts
  `next(iter(...))` — the oldest-inserted key. So a counter is evicted on age, not liveness, and
  eviction silently resets that run's consult budget to zero.
- **Evidence:** confirmed mechanically — after inserting `old_run`, `new_run`, then re-charging
  `old_run`, the order is still `['old_run', 'new_run']` and `_prune` would evict `old_run`.
- **Bound (honest):** the map is capped at `_MAX_TRACKED_RUNS = 512` and keys are never removed on
  completion, so triggering this needs 512 distinct runs to start within one run's lifetime.
  Unlikely on a daily driver; worth fixing while the file is open.
- **Fix:** `self._consults.pop(key, None)` before re-inserting, or evict by the stored monotonic
  start.
